## 制御遅延に対する耐性がゼロだった（18:10 追記）

mujoco の GUI（C++/DDS 経路）で手動操作すると「跳ぶが着地で前に転ぶ」ばかりで、
python 自動評価の着地 48% が再現しない、という報告から調べた。

まず python 側の 48% が測り方の甘さでないことを確認した:

| 条件 | 跳躍成立 | 着地成功 |
|---|---|---|
| 観測窓 3 秒（既定） | 78% | 48% |
| 観測窓 **6 秒** | 78% | 48% |
| 助走 6 / 8 / 12 秒 | 85 / 92 / 90% | 48 / 52 / 42% |

窓を倍にしても数字が動かず、成功試行の最終傾きは 0〜2 度。**着地後に遅れて転ぶ個体はいない**。

**違いは制御遅延だった。** `mujoco_jump_eval.py` に `--action-delay`（指令を N 制御ステップ遅らせる）を
追加して測ると:

| 遅延 | 跳躍成立 | 着地成功 | 飛距離 | 実測助走 |
|---|---|---|---|---|
| 0 ステップ（従来の測り方） | 78% | **48%** | 1.338 m | 2.90 m/s |
| **1 ステップ（20 ms）** | 35% | **5%** | 0.359 m | **1.47 m/s** |
| 2 ステップ（40 ms） | 5% | 0% | −0.005 m | — |

**C（飛距離重視）は 1 ステップ遅延で跳躍成立 0%。** D も助走速度が半減し、走行中に転ぶ試行が並ぶ
（最終傾き 94〜99 度）。**20 ms の遅延で走行そのものが壊れる。**

原因は学習側にある: **`source/.../tasks/` に行動遅延・観測遅延のモデルが1つも無い**（grep 済み。
`assist_delay_s` は EFGCL 補助のもので別物）。トルク・質量・摩擦は DR しているが、**遅延だけ素通し**だった。
python 評価も同期ループで遅延ゼロなので、**学習・評価の両方が遅延ゼロという同じ前提を共有していた**。
C++/DDS 経路と実機には必ず遅延があるので、そこで初めて破綻が見える。

**含意: このパッケージの2本は実機に出せる状態ではない。** 着地 48% は「遅延ゼロなら」の数字。
直し方は学習側で行動遅延をランダム化（0〜2 ステップ）して学習し直すこと。
**C++ 経路の実際の遅延量はまだ測っていない**（`/tmp/go2_ctrl_session.log` に JUMPTRACE を採る準備はした）。

### C++ 経路の実測トレース（18:25）

go2_ctrl をログ付きで起動し、手動で5回跳ばせた（`/tmp/go2_ctrl_session.log`、JUMPTRACE 351行）。

- **制御周期は 20.00 ± 0.00 ms**（ジッタなし）。遅れの正体はループの乱れではなく、
  「状態を読む → 指令が効くのは次の周期」という**構造的な1ステップ**。
- **5回とも転倒**（`bad_orientation -> Passive`、最終 tilt 1.03 / 2.15 / 2.07 rad）。
- 崩れ方は共通で、**着地ではなく空中**で決まっている:

| t [s] | 何が起きているか |
|---|---|
| 0.02〜0.20 | 正常に走っている（tilt 10度前後） |
| 0.22〜0.32 | 踏切（`dq_max` が 50〜56 rad/s に跳ね上がる） |
| 0.32〜0.85 | **tilt が 20→40→60度と単調に増える。この間 `dq_max` は 1〜4 rad/s**＝脚はほぼ静止 |
| 0.85〜 | 着地（接地）だが、すでに前のめり。2回は 145〜170度まで回って裏返った |

**踏切の瞬間に前向きのピッチ角運動量が入っていて、空中では直せない**（脚は胴体ピッチ慣性の79%を
占めるが、畳む/伸ばすで慣性は±6%しか動かない → [[reference_aerial_reorientation]]）。
python 側で遅延1ステップを入れたときの「走行中に転ぶ・最終傾き94〜99度」と同じ壊れ方で、
**遅延仮説と整合する**。
