## サイクル2で分かったこと（2026-09-15 04:20）

**着地の飴を5倍にしたら跳躍そのものが壊れた。** 飛距離 1.929 → 0.478 m、跳躍成立 85% → 10〜32%。
着地して初めて入る大きな飴は「思い切って跳ぶ」の期待値を下げる——崩れる跳躍はその飴を丸ごと失うので、
**跳ばない・小さく跳ぶが最適解に寄る**。Isaac 側では距離 1.20 → 0.95 の緩やかな低下にしか見えず、
mujoco で初めて崩壊が見えた（Isaac が実機を予測しない例、今夜これで2つ目）。

**同じ変更を Anaguma に入れた run は健全**（着地の飴の収入 0.64〜0.75、距離 0.90 → 0.97、real_jump 0.75 維持）。
つまりこれは Go2 の動作点（助走 5.0 m/s・頂点 0.386）に固有の壊れ方。

**着地を直接買う試みはこれで4回連続の失敗**（踏切対称性 Loop30 / 着地スタッガ / 着地衝撃 Loop33 / 着地の飴5倍）。
5回目は着地そのものではなく**着地を難しくしている入力（踏切 v_z）**を縛る ＝ サイクル3。

**運用メモ**: サイクル3のスモークで、新項が `-square(...)` を返しつつ weight も −10 にしていたため
**報酬が +0.163（上限超過ほど得）になっていた**のを実測で検出・修正した。この codebase は
「関数が正の大きさを返し、罰は RewTerm の負 weight が担う」側の約束（`jump_dense_reward` だけが逆で、
あちらは関数側に符号がある）。**新項は必ずスモークで符号と桁を実測すること。**

## サイクル3で分かったこと（2026-09-15 06:35）— Go2 の着地は Isaac 側の量では動かない

v_z 上限ペナルティは **Isaac では完全に狙いどおり働いた**（収入 −0.08〜−0.11、離陸の配分が
v_x 側へ 2.77→3.16 / v_z 2.09→2.25）。にもかかわらず **mujoco の頂点は 0.25〜0.31 のまま動かず、
着地も 2〜8% のまま**。飛距離だけが 1.929 → 1.1〜1.68 に落ちた。

Anaguma 側で見つけた「Isaac に無い分布は Isaac の報酬では触れない」がここでも出た形。
Go2 はさらに **助走そのものが Isaac 指令 2.8 に対し mujoco 実測 5.0 m/s** で、
**着地を壊している動作点が Isaac には存在しない**。着地を直接買う試みはこれで **5連敗**
（踏切対称性 Loop30 / スタッガ / 着地衝撃 Loop33 / 着地の飴5倍 / v_z 上限）。

**この夜の結論として記録しておく**: 報酬関数だけで Go2 の mujoco 着地率を上げる道は、
今夜試した範囲では見つからなかった。残る現実的な手は (a) 距離側の動機を切って着地に振る
（サイクル4）、(b) 報酬の外——助走帯や DR といったタスク設定（今回のルールでは触れない）。

## サイクル5（2026-09-15 14:38〜）— 報酬の全面棚卸し

ユーザー指示「高さを追求する過程で導入した報酬が飛距離と矛盾していないか、逆に Loop 10 までは
効いていたのに落とした報酬が無いか、徹底的に洗い直せ」。各 run の `params/longjump_env_cfg.py`
スナップショットから重みを時系列で抽出し、実測収入（`Episode_Reward/*`）と突き合わせた。

### 分かったこと

**1. `jump_foot_clearance`(10.0) は飛距離路線では不要かつ有害。** 目的関数 `2*v_x*v_z/g` に
クリアランスは入らない。導入理由(Loop 26)は「人が見て高く見えるのは足の下の隙間だから」＝
**高さ路線の見栄えの項**で、Loop 47 で目的関数を飛距離に戻したときに外し忘れていた。
収入 +0.411（目的関数 +2.06 の20%、正の項で2番目）。有害な理由は脚が Go2 の pitch 慣性の
79% を占めること（空中で畳む＝胴体が回る）。**Loop 44 でこの重みを 16.0 にしたとき
転倒 0.12% -> 22.9% で run が崩壊している**のが決定打。mujoco の失敗は傾き150〜176degの前転が大半。

**2. `jump_height`(4.7, target 0.30) は飽和した上に v_z の天井になっていた。**
Isaac 実測 0.287 に対し Gaussian は 0.99 = 勾配ゼロ（jump_takeoff_speed(L11)、
jump_takeoff_apex(L16) を殺したのと同じ飽和死）。さらにピーク型なので 0.30 を超えると
減点に転じる。等エネルギーで積が最大になるのは v_x = v_z、現在の踏切エネルギーでは
apex ≈ 0.41 m なので、**目的関数が要求する高さより低い位置に蓋をしていた**。

**3. L10（飛距離ベスト `model_9400`、着地96.9%・転倒0%）には、いまの飛行/着地整形6項
（foot_clearance / flight_pitch / landing_gear / landing_order / roll_rate / leg_contact）が
1つも無かった。** 全部が高さ路線で足されたもので、着地率はその後 96.9% -> 12% に単調低下。
うち4項は収入 0.00x で実質不活性（＝害も無い）ので残す。

**4. 「L10 にあって今ない必要な報酬」は無かった。** `jump_takeoff_speed`(2.5) は L11 で
外されているが、理由は `clamp(v_x/2.0)` の飽和で、積がそれを内包している。復活させても即飽和。
**足りない報酬は無く、余計な報酬がある側だった。**

**5. これが発散（サイクル2〜4）と同じ根。** PPO cfg の `entropy_coef` のコメントに
Loop 21〜27 で繰り返した崩壊機構が記録されている——**タスク報酬が飽和して平らになると、
生きている勾配がエントロピー項だけになり、方策が広がる方向にしか動けなくなって崩壊する**。
昨夜の署名（action noise std 0.34 -> 0.79、action_rate 爆発）はこれ。サイクル4は目的関数を
意図的に飽和させたので最も激しく発散した（発散 iteration 数 サイクル2=16 / 3=88 / 4=2416、
飽和の度合いと一致）。**飽和した項を放置することが、頭打ちと数値発散の共通原因。**

- **高さ関連の数値は一切無視する**（`max_height_gain` / 頂点 / apex / foot_clearance）。
  上がっても下がっても判断材料にしない。
- **着地率・跳躍成立率は記録するが、最適化の対象にしない。** 診断として書き残すだけ。

## 各サイクルの手順

1. **完走待ち**: `pgrep -f "train[.]py --task Unitree-Go2-LongJump"`（角括弧で自己マッチ回避）。
2. **健全帯の特定**: ログを走査し、崩壊の署名（`Mean action noise std` が 0.35 超へ上昇、
   `Episode_Reward/action_rate` が −5 を下回る）が出る直前までを健全帯とする。
   その帯の中から `unaided_jump_distance` のピーク付近を含む3〜5点を候補にする。
3. **mujoco実測**: `scripts/export_go2_candidates.sh` → `scripts/eval_go2_loop_mujoco.sh`
   （40試行 @vx2.8）。**評価器は角速度修正後のものを使う**（2026-09-15に修正済み）。
4. **予測との突き合わせ**: 前サイクルで書いた仮説と予測値に対し、実測がどうだったかを
   この台帳に1行で書く。**当たった/外れたを明示する。**
5. **次の1点を決める**: 変更は**1サイクル1点**。決める前に必ず次を書く。
   - 仮説（なぜその項が飛距離を動かすと考えるか）
   - **予測**（その項の収入がいくらになり、飛距離がどちらへ何%動くか）
   - 反証条件（何が起きたらこの仮説は間違いか）
   優先順位: ①既に weight 0 で眠っている項（外した理由が実測で記録されている）→
   ②既存項の weight/params → ③新規関数（最後の手段）。
6. **スモーク**: 60 iter で新項の**符号と桁を実測**し、狙いの収入帯に weight を合わせる。
   `jump_dense_reward` 以外は「関数が正の量を返し、罰は負 weight が担う」約束。
7. **本番投入**: 起点は**mujoco飛距離が最良の健全チェックポイント**。
   `ITERS=1500`（崩壊がresume後1200〜1900で来るため3000は無駄）。
   `START_RUN=<run> START_CKPT=<ckpt> ITERS=1500 bash scripts/run_go2_loop_cycle.sh`

## 守ること

- **タスク設定は触らない**（助走帯・assist・env数・Net2Net起点）。報酬関数のみ。
- 報酬を足す前に「**この項で何が起きるはずか**」を書く。書けないなら足さない。
- 崩壊が起きても run 自体は失敗ではない。**崩壊前の帯から候補を拾えば成果は残る**
  （サイクル5の記録 1.761 m は崩壊 200 iter 前の個体）。
- 各サイクルの結果は必ずこの台帳に追記する。

## サイクル6（実行中、`2026-09-15_16-35-23`）の仮説と予測

## サイクル12 結果 — **この学習は決定的だった。引き直しにはseed変更が必要**

サイクル10とまったく同じ条件（起点 `model_12400`、`entropy_coef` 0.002、300 iter）で回したところ、
**6点すべてがサイクル10と同一の数値**になった。ONNX を md5 で照合すると**ビット単位で同一**:

```
5a9e51ff040d2dbd3567c5b366c30fcb  eval_go2_cycle10/Tc_..._model_12550.onnx
5a9e51ff040d2dbd3567c5b366c30fcb  eval_go2_cycle12/Fc_..._model_12550.onnx
```

原因: `agent_cfg` の **seed が 42 固定**（ログの `Environment seed : 42`）。
`Environment seed : None` と読んでいたのは誤りで、None は CLI 引数の既定値、実際には 42 が入る。

**「くじ」という見立ては誤りだった。同じ起点・同じ設定の run は完全に再現する。**
→ **サイクル12は情報ゼロ。同じ条件で引き直すのは純粋な無駄。**
run ごとに違う結果を得るには `--seed` を変えるしかない。
`scripts/run_go2_loop_cycle.sh` に `SEED=<N>` を追加した（`SEED=1 START_RUN=... bash ...`）。

なお run 内のチェックポイント間のばらつきは実在する（点ごとの平均の幅 0.588 m: 1.165〜1.753）。
**「同じ run の中のどの点を拾うか」は効くが、「同じ run を引き直す」は効かない。**

1. **この学習は決定的**（`agent_cfg` の seed が 42 固定）。同じ起点・同じ設定の run は
   ビット単位で同一。**引き直しには `SEED=<N>` が必須**（`run_go2_loop_cycle.sh` に追加済み）。
2. **resume 起点の方策 std に窓がある**: **0.27〜0.34 が収穫帯**、0.23 は伸びず、
   **0.37 以上は即崩壊で全滅**。起点は飛距離ではなく **(飛距離, std≤0.34)** で選ぶ。
3. **最良個体は resume から +100〜150 iter**。run は 300 iter で足り、1500 iter は無駄。
4. **`save_interval` は 50**。100 刻みだとピークを踏み外す（平均の幅が run 内で 0.4〜1.0 m ある）。
5. **崩壊署名（`action_rate < −5`）は「終わり」ではなく「収穫期の始まり」**。
   署名の 100〜200 iter 後に最良が出る。
6. **平均を縛るのは水準ではなくばらつき**。単発では **2.931 m** 跳べており、
   **2.06 m は物理的に届く**。足りないのは一貫性。
   ただし起点を更新していけば平均とばらつきは同時に良くなる（距離std 0.284 → 0.177）。

## 残っているレバー（報酬の外）

報酬と収穫の枠内では 1.98 m 前後で飽和した。ここから先に効く可能性があるのは:

- **助走帯**（現在 U(2.8, 3.3) m/s）。ただし据え置きベストは助走 5.0 m/s で 1.674 m だったので
  **単純に上げれば伸びるわけではない**（記録個体は助走 2.8 m/s で 1.977 m を出している）。
- **アクチュエータモデル**。mujoco には関節速度上限もトルク–速度曲線も無く、
  Isaac は 13.5 rad/s から低下する。**単発 2.9 m がこの差に乗っている可能性**があり、
  実機で同じ距離が出る保証はない。実機前に Isaac 側の T-N 曲線で検算すべき。
- **DR**（ドメインランダマイゼーション）。ばらつきの主因が踏切の再現性なので、
  DR を強めて「どの初期条件からも同じ踏切」を学習させる方向。

**いずれもユーザー指示の「報酬のみ」の枠外なので、判断を仰ぐ。**

# v_z ギャップの追跡（2026-09-16）— 学習の物理刻みが粗すぎた

アクチュエータの検証で残った「同じポリシーの離陸 v_z が Isaac 1.44 / mujoco 2.18」を追った。

## まず判定を揃えた（指標の定義の差ではなかった）

Isaac の `liftoff_vel_z` は窓内で最も v_z の大きい離陸を latch するが、mujoco は real_jump ゲートを
最初に満たした滞空を採る。`scripts/rsl_rl/jump_trace_isaac.py` で **Isaac 側も mujoco と同じ後処理**
（滞空≥0.20s かつ 上昇≥0.08m を満たす最初の滞空、直前の連続接地を踏切）に揃えた。

| 同じ `model_12700`・同じ判定 | Isaac (sim.dt 0.005) | mujoco |
|---|---|---|
| 離陸 v_x / v_z | 2.793 / **1.379** | 3.19 / **2.18** |
| 積 v_x·v_z | 3.851 | **6.95** |
| 滞空 / 上昇 | 0.564 s / 0.121 m | 0.732 s / 0.230 m |
| 踏切の接地時間 | 155 ms | 97 ms |
| 踏切中の膝の速度ピーク | **13.6 rad/s** | **32.8 rad/s**（制御レート間引きで揃えた値） |

Isaac の latch は「最も強い離陸」を採る＝Isaac に有利な定義なのに差が残る。**軌道そのものが違う。**

## 単一変数で潰した

| 条件 | v_x | v_z | 積 | 弾道 2v_xv_z/g | 膝ピーク |
|---|---|---|---|---|---|
| 基準 (sim.dt 0.005, torque_scale 1.0) | 2.793 | 1.379 | 3.851 | 0.785 m | 13.6 |
| torque_scale 1.2（mujoco の ctrlrange 相当） | 3.021 | 1.502 | 4.537 (+18%) | 0.925 m | 14.5 |
| **sim.dt 0.002（mujoco と同じ）** | 3.179 | 1.692 | **5.380 (+40%)** | 1.097 m | 15.5 |
| 両方 | 3.357 | 1.798 | 6.035 (+57%) | 1.230 m | 15.4 |
| （参考）mujoco | 3.19 | 2.18 | 6.95 | 1.418 m / 実測 1.977 m | 32.8 |

## 刻みの収束確認

| sim.dt | v_z | 積 |
|---|---|---|
| 0.005（学習の既定値） | 1.379 | 3.851 |
| 0.0025 | 1.616 | 4.874 |
| 0.002 | 1.692 | 5.380 |
| 0.001 | 1.741 | 5.444 |

**0.002 → 0.001 で積は +1.2% しか動かない＝0.002 でほぼ収束。0.005 は収束値より 29% 低い。**
踏切は 100〜160 ms しかないので、0.005 では 20〜30 ステップしか刻めず接触の力積を取りこぼしている。

## 結論

Isaac↔mujoco ギャップ（積 3.851 → 6.95）の内訳:

- **+40% は Isaac 側が粗すぎた分**（sim.dt 0.005 → 0.002）。**これは Isaac の誤り**で、直すべきは学習側
- **+12% は mujoco 側が甘い分**（ctrlrange 45.43 が Isaac の押す側上限 Y1 39.22 より 16% 高い）。
  **実機は Isaac 側が正しい**ので、記録 1.977 m はこのぶん上振れしている
- **残り 15% と、膝の速度 15 vs 33 rad/s は未解明**

`sim.dt = 0.005` は上流の `velocity_env_cfg.py:397` 由来で、**このリポジトリの Go2 ポリシーは全部これで学習している。**

### 注意
- 同じポリシーを刻みだけ変えて測った結果であって、0.002 で学習し直せば良くなるとは限らない（別の方策になる）。
- torque_scale 1.2 は学習時の DR 範囲 (0.8-1.2) の内側なので分布外ではないが、**実機相当は 1.0**。
