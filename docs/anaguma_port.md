# Anaguma への走り幅跳びポリシー移植

ALTs の4足ロボット **Anaguma** に、Go2 で開発中の走り幅跳びポリシーを移植する作業記録。
判断は MuJoCo の実測で行う（Isaac の指標は実機挙動を予測しないことが Go2 側で確認済み）。

最終更新: 2026-09-14

## 1. 機体 — Go2 との違い

| | Anaguma | Go2 |
|---|---|---|
| 総質量 | 24.31 kg | 約 15 kg |
| 上腿 / 下腿 | 0.300 / 0.258 m | 0.213 / 0.213 m |
| 関節トルク上限 | 70 N·m | 45.43 N·m（膝） |
| **関節速度上限** | **13.4 / 15.6 rad/s** | **30 rad/s** |
| base 原点 | 機体前端（CoM は 0.275 m 後方） | CoM 位置 |

**力では有利、速度では不利。** 踏切に必要な脚の伸展速度に対する余裕が Go2 の 1.54 倍に対し
**1.14 倍しかない**（Go2 の踏切では膝が 37〜58 rad/s 回る）。
エネルギー法の理論値は頂点 63 cm / 飛距離 2.36 m（助走 2.0 m/s）で、いずれも Go2 の約1.17倍。
**予測: 高くは跳べるが、素早くは跳べない機体。**

## 3. 踏んだ罠

移植で時間を取られたのは全部ここ。

### URDF（受領時点）
1. **座標系が標準でない。** base_link は「前 = +z / 左 = −y / 上 = +x」。
   `M = [[0,0,1],[0,-1,0],[1,0,0]]` で `p_std = M p_urdf`、慣性テンソルは `M I Mᵀ`。
2. **effort / velocity limit が `1000000` のダミー値。** 実測値（70 N·m、13.4 / 15.6 rad/s）を入れ直す。
   **どの関節が 13.4 でどれが 15.6 かは社内docに記載がなく未確認**（hip/thigh=13.4、calf=15.6 と仮置き）。
   跳躍はアクチュエータ飽和が効くので要確認。
3. **前脚と後脚が鏡像構成。** 同じ関節角で前後に開脚して潰れる。IK は4脚それぞれで解く。

### 関節順
MJCF のボディ順は **FL, FR, RL, RR**、Unitree SDK / actuator は **FR, FL, RR, RL**。
`d.qpos[7:19]` をそのまま PD に渡すと別の関節を掴む。必ず関節名から `jnt_qposadr` / `jnt_dofadr` を引く。

### コリジョン形状
視覚メッシュをそのまま collider にすると**可動域内のランダム姿勢の 92%、立ち姿勢ですら自己干渉**する。
真因は形状ではなく配置——**大腿の付け根 y = ±0.1175 が胴体幅 ±0.146 の内側**にあり、凸包にすると
実機の側面の窪みが埋まって脚の付け根を飲み込む。

| リンク | 形状 |
|---|---|
| base | box 474 × **120** × 225 mm（幅だけ脚の取付位置より内側に絞る） |
| thigh / calf | 円柱 r44 L220 / r22 L236 mm |
| foot | 球 r31 mm（MuJoCo / Isaac で同じ球にして接触を揃える） |

立ち姿勢 100%→0%、全可動域 92%→32%。30iter スモークで episode 長 77.6→317.1、reward 2.92→15.98。

### IsaacLab 側
1. **`train.py` はタスクIDに "Unitree" を含むものしか `--task` の候補にしない。**
   `Anaguma-*` は登録済みでも `invalid choice` で弾かれる。`train.py` と `list_envs.py` に追加済み。
2. **`base_height_l2` → `base_com_height_l2` が必須**（base_link が CoM 位置にない）。
3. **Go2 の Stage B 設定をそのまま継承すると跳ばない。** → §4-1

### MuJoCo 側（2026-09-14 発見）
**`<motor>` に `class="anaguma"` が付いておらず、`<default>` の `ctrlrange="-70 70"` が届いていなかった。**
MuJoCo は `ctrlrange = [0, 0]` と解釈するので、ctrlrange でクリップするコントローラ
（`scripts/mujoco_jump_eval.py`）は**トルクを常に 0** にする——ロボットが1ミリも動かない。
`childclass` は body / joint / geom には伝播するが `<actuator>` は body ツリーの外なので届かない。
go2.xml は全 `<motor>` に class を書いている。`build_mjcf.py` ごと修正済み
（バックアップ `anaguma.xml.bak_no_motor_class`）。`stand_test.py` が動いていたのはクリップしないため。

## 4. 学習

**構成**: blind policy（固有受容のみ）／Stage A → Net2Net → Stage B の2段／Explicit Estimator／
EFGCL（踏切の瞬間に外力を加えて跳躍を物理的に実演し、学習に応じて 0 まで抜く）／
**外力なしの env を 25% 常設し、判断は `unaided_*` のみで行う**。
目的関数は**高さ**（`jump_takeoff_apex` weight 50 / 目標 0.40 m）。Go2 側は 2026-09-14 に飛距離へ
切り替えたが Anaguma は高さ重視のまま（両方 explicit に上書きしている）。

### 4-1. EFGCL 補助の強さ — from-scratch では桁で足りなかった

`real_jump` の判定は**滞空 0.20 秒以上 かつ 上昇 0.08 m 以上**で、跳躍報酬は全部このゲートの内側にある。
つまり**一度も跳べない機体には `jump_takeoff_apex`（weight 50）を含め何も払われず、跳ぶと
`lin_vel_z` 等の罰だけ食らう**ので、ポリシーは跳躍を抑え込む。補助はこの最初の一回を作る役。

Go2 の既定値 `assist_apex_height_m = 0.10` は「Go2 で実測 0.24 m」を根拠にした値だが、
**その実測は自分で踏み切れるポリシーの上で取ったもの**。踏切ゼロの機体では合成が効かず
同じ設定で 0.041 m しか出ない。両機体で測り直した（各 40 iter / 512 env / Net2Net 直後起点）:

| 機体 | 設定 | 上昇 | 滞空 | real_jump | 転倒 |
|---|---|---|---|---|---|
| Go2 | 0.10 | 0.041 m | 0.13 s | 6.8% → 0% へ減衰 | 小 |
| Go2 | **0.35 採用** | 0.157 m | **0.356 s** | **76.0%** | 38.9% |
| Go2 | 0.50 | 0.154 m | 0.275 s | 54.2% | 47.8% |
| Anaguma | 0.15 | 0.067 m | 0.09 s | 5.4% → 0% へ減衰 | 小 |
| Anaguma | 0.35 | 0.102 m | 0.154 s | 35.4% | 17.8% |
| Anaguma | **0.50 採用** | 約 0.24 m | 約 0.25 s | 約 55% | 約 32% |
| Anaguma | 0.55 | 0.274 m | 0.272 s | 61.8% | 36.5% |

**応答は単調でない。** Go2 は 0.50 より 0.35 のほうが滞空も跳躍率も高く転倒は少ない——
強すぎる外力は機体を飛ばすのではなく**回す**。「強くすれば跳ぶ」は成立しないので必ず測る。

**見るべきゲートは上昇量ではなく滞空時間。** Anaguma は 0.15 で上昇 0.067 m（閾値 0.08 m の際）なのに
滞空 0.09 s（閾値 0.20 s）で全く届いていなかった。外力は胴体を持ち上げるが、脚が接地したままだと
滞空にならない。

転倒 30〜40% は踏切を一度も学んでいない段階の値で、v4 期の Go2 も同水準（35〜41%）。
v4 の失敗は転倒率ではなく**補助が最後まで抜けなかったこと**なので、対処は減衰側
（`real_jump` ゲート＋`force_zero_at_step` で 1500 iter で強制ゼロ）。

**`crouch_assist_force` だけ JumpCommand 内で質量スケールされていない**（launch 側は
`total_force = m*v0/duration` で質量スケール済み）。150 N は Go2 の 15 kg 用なので
150 × 24.31/15.0 = **243 N** に修正済み。

### 4-3. 収支を項別に読む — 踏切は 1 エピソードあたり −3.4 の赤字だった

補助の強さは 0.50 で足りていた（上表）。それでもポリシーが踏切を採用しなかったのは、**採用すると損をする報酬設計だったから**。
`2026-09-14_17-02-57` の iter 100（補助 0.90、`real_jump` 0.74＝実際に跳んでいる瞬間）の項別収支:

| 跳躍の飴 | | 跳躍の鞭 | |
|---|---|---|---|
| `jump_height` | +0.0875 | **`jump_dense_reward`** | **−3.4783** |
| `jump_landing_feet_first` | +0.0743 | `jump_landing_order` | −0.0777 |
| `jump_foot_clearance` | +0.0302 | `jump_flight_pitch` | −0.0317 |
| `jump_takeoff_apex`（重み50） | +0.0114 | `jump_landing_gear` | −0.0230 |
| **合計** | **+0.203** | **合計** | **−3.622** |

同じ報酬セットで走る Go2（`2026-09-14_17-02-52`、iter 10899、`real_jump` 0.71）は
`jump_takeoff_distance` +1.439 を筆頭に **+2.06 を稼ぎ、`jump_dense_reward` は −0.0064 しか払っていない**。
**同じ項が Anaguma では 540 倍重い。** 走る（alive +0.62／upright +1.14／tracking +0.89）より跳ぶほうが確実に損なので、
「跳ばずに走る」は**バグではなく最適解**だった。

原因は 2 つあり、どちらも Go2 の数字をそのまま継いだことによる。

1. **`jump_dense_reward` は報酬セットで唯一、質量で正規化されていない量**（−std(接地力) [N]）。Anaguma は Go2 の 1.62 倍の質量。
   さらに curriculum が `early_weight=2.5` を `decay_at_step=60000`（= iter 2500）まで掛け続けるので、
   cfg の `weight=0.5` ではなく**実効 2.5 が 3000 iter のうち 2500 iter を支配する**。
   そもそもこの項は「跳べる機体の踏切を左右対称に整形する」もので（論文でも Phase 2a→2b、跳べてから緩める順序）、
   一度も踏み切っていない機体には**試行そのものへの課税**にしかならない。
   → **`early_weight` を `late_weight` と同じ 0.25 に寝かせた。**
2. **`jump_takeoff_apex`（重み 50、跳躍側の最大の飴）の助走ゲートが、フェーズ1の助走帯と矛盾していた。**
   ゲートは `clamp((trigger_speed − 2.0)/0.5)` で **2.0 m/s 未満には一切払わない**のに、
   同日夕のフェーズ1で助走指令を `U(0.0, 3.3)` へ下げた。**「遅く跳べ」と設定で言いながら遅い跳躍には払わない**状態で、
   ログでもこの項の収入は全区間 0.0000、`unaided_approach_gate` も 0.0000。
   → **`approach_lo/hi` を (0.5, 1.5) に変更**（フェーズ2で助走帯を戻すときは (2.0, 2.5) に戻すこと）。
   **名前と実測対象のズレの 8 例目**で、7 例目と同じく報酬項ではなく**報酬とタスク設定の不一致**。

`target_apex` は Go2 の 0.40 のまま残した（補助ありの実測頂点 0.24〜0.27 に対し `progress` は 0.6 前後で死んでいない）。
一度に 2 つ以上動かすと次の run が読めなくなるため。

**順序が決定的だったことの裏取り**: curriculum は iter 2500 で `jump_dense_reward` を 2.5 → 0.25 に落とす。
実際 iter 2500 以降この項の支払いは −0.008 まで軽くなる。**それでも跳躍は戻らなかった**（`unaided_real_jump` は
iter 2999 まで 0.0000）。補助は iter 1500 で既にゼロなので、**税が重いのは教師が実演している間だけ、
税が軽くなるのは教師が去った後**という最悪の順序になっていた。重みの値そのものより、
この 2 つのスケジュールの前後関係が効いている。

### 4-5. 試行5は 48 iter で打ち切り、単位を直して試行6へ（2026-09-14 夜）

試行5 `2026-09-14_19-56-07`（dense の重みだけ 2.5 → 0.25）を本番 2048 env で流したところ、
**重みを 1/10 にしても足りていなかった**:

| iter 48 | |
|---|---|
| 飴（apex 0.092 / height 0.088 / feet_first 0.076 / clearance 0.041） | **+0.297** |
| `jump_dense_reward` | **−1.464** |
| その他の鞭 | −0.149 |
| **収支** | **約 −1.3（まだ赤字）** |

`real_jump` も 0.65(iter20) → 0.46(iter48) と試行4と同じ形で落ち始めたので **48 iter で打ち切り**。
**重みで殴るのではなく単位から出す**のが正しい直し方だった——`jump_dense_reward` は
−std(接地力)[N] で、飴の側は全部無次元。機体が重くなるほど鞭だけが効く。

→ `mdp.jump_dense_reward` に **`normalize_by_weight`（m*g で割る、既定 False で Go2 は不変）** を追加し、
Anaguma 側で True に。60 iter のスモークで **dense −1.46 → −0.0017**、飴 +0.33 に対して無視できる水準、
Go2 の −0.0064 とほぼ同じ位置に落ちた。本番 run **`2026-09-14_20-00-36`**（2048 env / 3000 iter）を実行中。

**次に疑うべきは報酬表ではなく「跳ぶとエピソードが終わる」コスト。** 正規化後のスモークでも
`real_jump` は 0.88(iter20) → 0.46(iter50) と落ちており、収支が黒字でも落ちている。
跳躍時の `base_contact` は 10〜28% あり、転べば残りのエピソード（alive +0.6 / upright +1.1 /
tracking +0.9 のほう）を丸ごと失う。**跳躍の飴 +0.3 はこの機会損失より桁が小さい。**
本番で `unaided_real_jump` が黒字のまま 0 に落ちるなら、原因は報酬表ではなくこれ。

**この run で効いた変更は 2 つだけ**（§4-3・§4-5）: `jump_dense_reward` の m*g 正規化と、

**4回の失敗は補助の問題ではなく、報酬の単位とゲートの問題だった。**

## 6. フェーズ2以降 — 自律ループ4サイクルで**成功条件を達成**（2026-09-14 夜 〜 2026-09-15）

判定は必ず mujoco（Isaac の数字は実機を予測しない、というのがこのプロジェクトの確定知見）。

**頂点が低いまま距離が出ている**のがこの個体の特徴。

### 効いた変更と効かなかった変更

| サイクル | 変更 | 結果 |
|---|---|---|
| 2 | **目的関数の入れ替え**: `jump_takeoff_apex` 50→0、`jump_takeoff_distance` 0→74(target 2.06) | **0.987 → 1.266 m、着地 78 → 90%**。当たり |

**サイクル2が唯一の当たり**で、中身は「報酬が測っている量を判定基準（飛距離）に合わせた」だけ。
Go2 の Loop 47 と同じ入れ替えで、伸びたのは配分ではなく **v_x そのもの**（1.32 → 2.17）。

### この移植でいちばん重要な発見

**チェックポイントの当たり外れが、報酬変更の差より大きい帯がある。**
同じ run（サイクル3）の 100 iteration 刻みで着地率が
**`9900` 60% → `10000` 70% → `10100` 92%** と動いた。
`9600` と `10200` だけを見て「あと着地1ポイント」と判断し、サイクル4で報酬を変えたが、
**答えは同じ run の 100 iteration 隣にあった**。良さそうな run は 100 刻みで潰すほうが速い。

### Isaac 側では着地の良し悪しが見えない（報酬設計の限界）

mujoco で着地90%の `5800` と 69%の `9600` を Isaac の着地系メトリクス全部で比べても差が出ない:

| | `5800`(90%) | `9600`(69%) |
|---|---|---|
| upright_at_close | 0.898 | 0.890 |
| landing_max_tilt | 0.163 | 0.157 |
| landing_knee_contact | 0.889 | 0.937 |
| landing_impact_N | 488 | 434 |
| touchdown_vz | −0.54 | −0.42 |

さらに、mujoco で転倒している踏切 v_z 2.3〜2.4 相当の分布が **Isaac には存在しない**
（`jump_liftoff_vz_cap` を cap 2.0 でも 1.6 でも収入 0.0000）。
**「Isaac の量に報酬を付けて mujoco の着地を直す」道は原理的に細い。**

### 評価スクリプトの角速度バグ（2026-09-15 修正）

`scripts/mujoco_jump_eval.py` が観測の `base_ang_vel` を二重回転させていた
（MuJoCo の free joint の `qvel[3:6]` は既に胴体ローカル系なのに `R.T` を掛けていた）。
IsaacLab の `base_ang_vel` も deploy C++ の IMU gyro もローカル系なので掛けないのが正しい。
**Anaguma の数値は修正の影響がほぼ無かった**（`model_10100`: 1.349 → 1.377 m、着地 92 → 88%、
いずれも40試行のばらつきの範囲）。**Go2 側は順位が入れ替わるほど動いた**ので、
Go2 の数値と比べるときは修正後の値を使うこと。
