# 指示文・応答文データセットの作り方（手順書）

`Go2-Multitask-v2` を自然言語で操作する LLM を作るための、学習データの作成手順。
前段（プログラム生成と sim 検証）は `README.md` に、ここではその結果から
**指示文 + 応答文 + プログラム** の三つ組を作る手順を書く。

## 0. 全体像

```
validated.jsonl（プログラム + sim 実測）＋ capability.json（能力表）
   │
   ├─ 1. 分割        学習 / 評価をプログラム単位で分ける       build_dataset.py
   ├─ 2. 事実の整理  実測から「何が起こるか」を一文にまとめる   build_facts.py
   ├─ 3. 指示文生成  言い回し辞書から 3 つの口調で組み立てる     phrasebank.py
   ├─ 4. 往復検証    指示文 → プログラムに逆パースして照合       parse_instruction.py + roundtrip_check.py
   ├─ 5. 応答文生成  実測と能力表に基づく返事（警告・断り）      build_dataset.py + phrasebank.py
   ├─ 6. 負例の追加  雑談・不可能・過大要求・曖昧                negatives.py
   └─ 7. 整形と点検  学習用 JSONL と 7 項目の自動チェック        check_dataset.py
```

実行は 3 コマンド。

```bash
python scripts/llm/build_dataset.py --out data/llm/dataset.jsonl --total 5000
python scripts/llm/parse_instruction.py data/llm/dataset.jsonl -o data/llm/reparse.jsonl
python scripts/llm/roundtrip_check.py data/llm/dataset.jsonl data/llm/reparse.jsonl
python scripts/llm/check_dataset.py data/llm/dataset.jsonl
```

学習させるモデルの入出力は次の形に固定する。

```json
入力:  "5mくらい直進してから、バク転して"
出力:  {"reply": "了解、5m進んでからバク転するね。", "program": [{"skill":"move","dir":"forward","distance_m":5}, {"skill":"flip","kind":"backflip"}]}
```

雑談や断る場合は `"program": []`。

## 1. 入力データと分割

入力は `data/llm/validated.jsonl`。1 行 1 プログラムで、主に次を使う。

| フィールド | 使い方 |
|---|---|
| `program` | 学習の正解出力 |
| `passed`, `success_rate` | 合格なら通常の応答、不合格なら警告か断り |
| `timeline.duration_s`, `timeline.adjustments` | 応答に書く所要時間と、コンパイラが変えた点 |
| `motions[].measured_mean` | 実際に進んだ距離・角度 |
| `flips[].success_rate`, `stances[].success_rate`, `stances[].recover_s` | 危なさの根拠 |

分割は **プログラム単位** で 90 / 10。同じプログラムの言い換えが学習側と評価側に
またがると評価が甘くなる。`id` のハッシュで決めれば再現できる。

## 2. 事実の整理（fact sheet）

モデルに渡す前に、各プログラムについて機械的に「事実」を作る。生成モデルには
プログラム JSON ではなく、この事実を読ませる。数値が嘘になるのを防ぐため。

実装済み: `scripts/llm/build_facts.py`（`validated.jsonl` + `capability.json` -> `facts.jsonl`）。

例:

```
- 前へ 1.0 m/s で約 5.6 秒（実測 約 5.0 m 前進）
- 停止して静定 0.5 秒
- バク転 1 回（成功率 100%）
- 合計 約 8 秒
- コンパイラの調整: なし
- 判定: 合格（8/8）
```

不合格の場合は原因を添える。

```
- 倒立 5 秒（起立は成功。降りるときに 8 体中 5 体が転倒）
- 判定: 不合格（3/8）  理由: handstand の降りが不安定
```

能力表 `data/llm/capability.json` から、スキル単位の**一般的な**成功率も必ず添える。
これはこのプログラム固有の実測（複製 8 体、n=8）とは別物で、応答文の警告判定は
一般成功率の方を使う（次の「2.1」を参照）。

```
- 前方回転 1 回（このプログラムでは成功 8/8。能力表全体では 76%）
```

### 2.1 プログラム固有の実測 vs 能力表の一般成功率

n=8 の実測は**この 1 本のプログラムに限れば**正しいが、ノイズが大きい。frontflip は
ある回のプログラムでたまたま 8/8（100%）でも、能力表全体（n=2000 超）では 76% しか
ない、ということが実際に起きた。指示文には「前方回転して」としか書けず、モデルは
どの回のプログラムを実行することになるか実行前には分からないので、**警告を出すか
どうかは能力表の一般成功率で決める**。このプログラムの実測（8/8）を理由に警告を
省いてはいけない。

- 断る（program を空にする、または該当スキルだけ外す）: 一般成功率 10% 未満
- 軽く警告して挑戦する: 一般成功率 80% 未満
- 何も言わない: 80% 以上

`CapabilityTable.unreliable()` の閾値をこの二段で使う。

## 3. 指示文の生成

5000 件を 1 文ずつ手で書くのは現実的でないので、**言い回しを人が書き、組み立てを機械がやる**。

- `phrasebank.py` … 日本語の言い回しだけを持つ辞書。方向語・速さ語・技名・数の言い方・
  接続詞・語尾・返事の定型・警告文を、口調別に人が書く。数値も判断も持たない。
- `build_dataset.py` … 1 手順ずつ辞書に語を引きに行き、接続詞でつないで 1 文にする。
  何を断るか・何を警告するかは能力表と sim 実測だけで決める（言い回しは決めない）。

多様性はプログラム側から来る。検証済み 1404 本はすべて別の内容なので、同じ言い方の
テンプレートでも出来上がる文は毎回違う。実際、5000 件のうち入力文が一意なものは 92%
（重複はほぼ雑談と曖昧要求で、同じ挨拶に別の返事を付けたもの）。

1 プログラムにつき **3 種類** 作る。

| 種類 | 例 |
|---|---|
| 標準語・丁寧 | 「5 メートルほど前進してから、バックフリップをしてください」 |
| 関西弁・くだけた | 「5mくらい前いって、そっからバク転してや」 |
| 短い・省略あり | 「前5m、バク転」 |

指定すること:

- 数値は事実にあるものだけ使う。「5.6 秒」のような内部値は書かない。
- 方向は 8 方位か旋回の言葉で。細かい角度や速度の数値は使わない。
- 「ゆっくり」「速く」は speed に対応するときだけ入れる。
- 「その場で」「しばらく」「ちょっと」など曖昧語を混ぜる（人間はそう言う）。
- 順序を表す言葉（〜してから、そのあと、最後に）を自然に。
- 1 種類につき 1 文か 2 文。

## 4. 往復検証

指示文を、**書いたときの情報を一切使わずに** プログラムへ戻し、元と一致するか見る。
`parse_instruction.py` は語彙（「バク転」「左斜め前」「3m」「ゆっくり」…）だけを見る
正規表現のパーサで、`phrasebank.py` を import しないし、元のプログラムも読まない。
入力は各行の `input` だけ。

一致の基準（`grammar.py` の型で比較）:

- skill の列と kind / dir が完全一致
- speed は一致。ただし指示文に速さの言葉が無い場合、既定値（normal）と一致すれば可
- duration_s / distance_m / angle_deg / count は ±20% か、丸め（4.5 秒 ≒ 5 秒）を許容
- stop の長さは不問

落ちた指示文は捨てる。落ちる率が高いプログラムは指示文が書きにくい形（backward_right の
slow で 0.5 m など）なので、サンプラーの重みを見直す材料にする。

実装済み: `scripts/llm/parse_instruction.py`（逆パース）と `scripts/llm/roundtrip_check.py`
（一致判定。5.1 の部分拒否ルールと、雑談・不可能・曖昧は program が空であることの確認も含む）。

**この検証で分かること・分からないこと。** 言い回しと語彙はどちらも人（同じ書き手）が
書いたので、「自然な日本語か」はこれでは分からない。分かるのは
**文とプログラムが食い違っていないか** で、実際に次を検出した。

- 短文の「右5秒」が旋回とも横歩きとも読めた（→ 旋回は「右回り5秒」と書くよう修正）
- 関西弁の「はよ」が文頭の助詞として削られ、速さ語が消えていた
- 「3m歩いて」の m が単語境界に合わず、距離が秒数として読まれていた
- 過大要求の返事にあった「1回の指示で」の「1」が数量と区別できなかった

自然さの判定は 8 節のランダム抽出（人が読む）が担当する。

指示文には、sim が条件として使った情報を必ず含めること。360 度旋回のように
「1 回転」だけでは方向（左/右）を指示文が特定できない場合、モデルは実行前にどちらへ
回るか判断する根拠を持たない。sim は片方の方向でしか測っていないので、事実整理の
段階で使われている方向・姿勢などの条件は、必ず指示文の候補にも反映させる
（生成時にモデルへ「事実にある条件は指示文からも分かるようにする」と指定する）。

## 5. 応答文の生成

返事は指示文と同じ口調で 1 種類だけ作る。構成は固定で、
**開き + 何をするかの言い直し + 必要なら警告 + ときどき所要時間**。
言い直しは指示文と同じ辞書から別に引き直すので、指示文の丸写しにはならない
（短文口調だけは意図的に近い形になる）。所要時間を言うのは 2 手順以上の 35% だけ。
数値は sim が測った `timeline.duration_s` をそのまま丸めて使う。

| 状況 | 応答の方針 | 例 |
|---|---|---|
| 合格 | 何をするかを短く確認。所要時間か距離を 1 つ入れる | 「了解。5m前に進んでからバク転するね。8秒くらい」 |
| 不合格（危ないが挑戦する） | やるが、成功しないかもと一言 | 「倒立やってみるけど、降りるときに転ぶかもしれん」 |
| 不合格（できない） | 断って理由 | 「ジャンプはまだできへんねん。バク転なら行けるよ」 |
| **混在（できるスキルとできないスキルが混ざる）** | **できないスキルだけ断り、残りは実行** | 「ジャンプはまだうまくできひんくてこけてしまうから、そこは飛ばすで。バク転2回はやるわ」 |
| コンパイラが調整した | 何をどう変えたか | 「10回は多いから5回にしとくね」 |

「挑戦を断らない」方針は決定済み。断るのは能力表で**一般成功率**がほぼ 0 のスキル
（現状 jump）だけ。閾値は `CapabilityTable.unreliable()` を二段（断る 10% 未満、
警告 80% 未満）で使う（2.1 参照）。

### 5.1 混在する要求（部分拒否）

`validated.jsonl` の不合格プログラムの多く（例:「ジャンプ 3 回してからバク転 2 回」）
は、断るべきスキル（jump）と問題なく実行できるスキル（backflip）が同じプログラムに
混ざっているだけで、プログラム全体が悪いわけではない。この場合は元プログラム全体を
捨てず、次のように加工して学習例にする。

1. 元プログラムの各手順を、その `skill`/`kind` の一般成功率が 10% 未満かどうかで仕分ける。
2. 10% 未満の手順を取り除いた残りを、モデルの出力 `program` にする。
3. 応答文は、断った手順とその理由、実行する手順を両方言う。
4. 残りが 0 手順になる場合（要求全体が断る対象だけだった場合）は、`program: []` の
   完全な決り文句にする。「不合格（できない）」の行はこの場合。

指示文は元の要求どおり全部書く（「ジャンプを3回して、そのあとバク転を2回して」）。
指示文とモデルの出力プログラムが一致しないのはこのケースだけで、4 の往復検証は
この場合は次のルールに変える: 出力プログラムが「指示文を素直に読んだときの
プログラム（reparse）」から、断った手順だけを引いたものと一致するか、
かつ最低 1 手順は実際に断られているかを確認する。全部一致・何も断っていない
場合は「本来断るべきものを断っていない」ので不合格とする。

応答には実測にない約束を書かせない（「必ず成功する」「ぴったり 5 m」など）。

## 6. 負例

プログラムを出さない、または変える入力。**全体の 15〜20%**。

| 種類 | 件数 | 出力 |
|---|---|---|
| 雑談・無関係（天気、挨拶、質問） | 300 | `reply` のみ、`program: []` |
| 不可能な要求（階段、物を持つ、泳ぐ） | 220 | 断る、`program: []` |
| 過大な要求（バク転 10 回、倒立 30 秒、100 m 前進） | 170 | **要求どおりのプログラム** と、どこまでしかやらないかの説明 |
| 曖昧な要求（「動いて」「なんかして」） | 90 | 短い確認質問、`program: []` |

不可能な要求は文法にないスキルを要求するもの。雑談はロボットに関係ない内容と、
ロボットについての質問（「何ができる？」→能力表から答える）の両方を入れる。

過大な要求で**上限に切ったプログラムを出さない**のは、切るのがコンパイラの仕事だから。
モデルが黙って 5 回に減らすと、ユーザーは 10 回頼んだつもりのまま結果を見ることになる。
要求はそのまま出し、「10回は多いから5回までにするで」と口で言う。

中身は `negatives.py` に人が直接書く（雑談 25 話題・不可能 45 動作・曖昧 8 話題、
それぞれ関西弁と丁寧語の両方）。ここだけは sim も能力表も関係しないので全部手書き。

## 7. 整形と規模

学習用 JSONL、1 行 1 例。

```json
{"id": "s0-000123#kansai", "split": "train", "category": "normal", "style": "kansai",
 "input": "前へ3mくらい進んでから、バク転2回してや。",
 "output": {"reply": "...", "program": [...]},
 "source": {"program_id": "s0-000123", "passed": true, "kind": "paraphrase"}}
```

システムプロンプトは行に持たせず `data/llm/system_prompt.txt` に 1 つだけ置く
（文法仕様 `describe_grammar()` ＋ 守ること）。学習時に各行の前に付ける。

実際に作った 5000 件の内訳:

| カテゴリ | 件数 | 内容 |
|---|---|---|
| `normal` | 3293 | 警告も断りも要らない |
| `partial_decline` | 408 | ジャンプだけ外して残りを実行 |
| `chitchat` | 300 | 雑談・挨拶・ロボットへの質問 |
| `minor_caution` | 247 | 前方回転（76%）を含む。軽く警告して実行 |
| `risky_attempt` | 230 | 倒立（降り 41%）を含む。強めに警告して実行 |
| `impossible` | 220 | 文法にない依頼を断る |
| `over_ask` | 170 | 上限超え。要求どおり出して、切る旨を返事で言う |
| `ambiguous` | 90 | 聞き返す |
| `declined` | 42 | ジャンプだけの要求。`program: []` |

口調は関西弁 1861 / 丁寧 1682 / 短文 1457。分割は train 4532 / eval 468
（プログラム `id` のハッシュで 90:10。同じプログラムの言い換えは必ず同じ側に入る）。

件数を変えるときは `--total`。プログラムが足りなければ `sample_programs.py` で増やして
再検証する（生成は数秒、sim 検証は 2000 本で 15 分）。

## 8. 品質チェック（学習前に必ず）

`check_dataset.py` が 7 項目を見る。1 つでも落ちたら非ゼロ終了。

| 項目 | 内容 |
|---|---|
| grammar | 全出力プログラムが `unitree_rl_lab.program` で parse・validate できる |
| declined | 一般成功率 10% 未満のスキルが出力に残っていない |
| cautions | 80% 未満のスキルを含む行に警告文がある。**含まない行に警告文が無い**（言っていない危険をでっち上げないこと） |
| numerals | 返事の数値がすべて根拠を持つ（プログラムの値、sim の所要時間 ±2 秒、コンパイラの上限、要求された値のいずれか） |
| forbidden | 「必ず」「ぴったり」「絶対」「確実に」「100%」が無い |
| duplicates | 同一の (入力, 返事, プログラム) が無い |
| balance | カテゴリ・口調・分割・入力の一意率を出す（目で見る用） |

これに加えて人がやること:

- ランダムに 20〜50 件抜いて読む。自動チェックは自然さを判定できない。
- 評価分割で、ファインチューニング前のモデルに指示文→プログラムをさせてベースラインを取る。
- 学習後は sim で実行して、生成されたプログラムが本当に立って終わるかを見る（未実施）。

## 9. 決めたこと / 残っていること

決まったもの:

1. 生成は外部 API を使わず、言い回し辞書＋組み立てで作る（3 節）。
2. 口調の比率はほぼ 1:1:1（関西弁がやや多い）。
3. 返事の口調は指示文に合わせる。
4. 断るのはジャンプのみ。倒立は警告して必ず挑戦する。

残っているもの:

1. ファインチューニング対象モデルの選定 → 要件は `MODEL.md`。実行場所は Go2 オンボード
   （Jetson）、出力順は `reply` 先のままに決定済み。候補は Qwen2.5-1.5B-Instruct と Qwen3-1.7B。
2. 学習後の sim での end-to-end 評価。
3. ロボット側の実行器（`Timeline.events()` を食わせる部分）。
