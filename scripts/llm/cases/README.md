# 失敗ケースを埋める ― ケースによらない一本の手順

実演で落ちた言い方を、**どのケースも同じ手順で**埋める。ケースごとに違うのは
`<NN-slug>/PROMPT.md` ― 人が書く1枚のシステムプロンプト ― だけ。症状も原因もその中に書く。

## 置き場所

```
scripts/llm/cases/<NN-slug>/PROMPT.md   ケース専用のシステムプロンプト。人が書く。git に入る
$JOB/case_out/<NN-slug>/batch_NN.jsonl  エージェントの生出力。使い捨て
$JOB/case_out/<NN-slug>.jsonl           集めたもの。人が目視する対象
```

`NN` は見つかった順の通し番号。**仕様（プロンプト）だけが git に入る。** 出力は採用が決まるまで
`$JOB` に置いたままにする ― 採り直すかもしれないものをリポジトリに置かない。

## 手順

```
0. 書く    scripts/llm/cases/<NN-slug>/PROMPT.md を人が書く（唯一のケース固有作業）

1. 生成    PROMPT.md を渡してエージェントに書かせる。1エージェント10行、10並列で100行。
           検査は一切走らせない（HANDWRITTEN.md §6）
           → $JOB/case_out/<NN-slug>/batch_NN.jsonl

2. 集める  cat $JOB/case_out/<NN-slug>/batch_*.jsonl > $JOB/case_out/<NN-slug>.jsonl

3. 目視    python scripts/llm/show_handwritten.py $JOB/case_out/<NN-slug>.jsonl --sample 10
           人が10件読む。9件以上あってたら採用。足りなければ 0 か 1 に戻る
```

ここまで。採用したものをデータセットに入れる工程は、採用が決まってから考える。

構造検査（`check_handwritten.py`）は 2 と 3 の間でも後でもよいが、**1 の最中には絶対に走らせない**。
ツールを書く工程に入れると書き手はそのツールの語彙に収束する ― 最初の手書き2036件がそれで失敗した。

## なぜ「10件で9割」でよいか

100件を全部検算するのは人間が続かんし、続かん検査は結局やらん。ケースデータの役目は
**その現象を1つも見たことがない状態から抜け出すこと**で、9割あっていれば分布としては十分に効く。
残り1割の間違いは、次の実演でまた出てくる。
