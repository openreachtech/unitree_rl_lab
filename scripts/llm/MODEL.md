# ファインチューニング対象モデルの要件

`data/llm/dataset.jsonl`（5000 件）で学習させるモデルを選ぶための要件。
データの作り方は `DATASET.md`、パイプライン全体は `README.md`。

## 1. タスクの性質

入力は日本語 1〜2 文、出力は JSON ひとつ。

```
入力   「5mくらい直進してから、バク転して」
出力   {"reply": "了解、5m進んでからバク転するね。", "program": [{...}, {...}]}
```

閉じた語彙（5 スキル・8 方位・3 速度・5 技・2 姿勢）への写像と、短い返事。
**知識も多段の推論も要らない。** 必要なのは、日本語を崩れた JSON にしない構文の安定性と、
学習データに無い言い回しへの汎化。

実測（Qwen2.5 のトークナイザ、5000 件）:

| | p50 | p95 | max |
|---|---|---|---|
| システムプロンプト | 690 | 690 | 690 |
| 入力 | 16 | 46 | 77 |
| 出力 JSON | 79 | 147 | 206 |
| 合計 | 785 | 883 | 973 |

→ **文脈長 2048 で十分**（1024 でもほぼ入る）。長文脈性能は選定基準にならない。

## 2. 必須要件

1. **instruct / chat 版であること。** 雑談は 300 件しか教えないので、「今日はいい天気だね」
   への返事の自然さはベースモデルの地力がそのまま出る。base モデルからは作らない。
2. **日本語が書けること。** 関西弁の生成は学習データが型を与えるが、崩れた敬体と
   ですます混在を避けられる程度の日本語力は前提。
3. **構造化出力に対応した推論系で動かせること。** llama.cpp (GBNF) / vLLM (XGrammar) /
   Outlines のいずれかで文法制約デコードをかける。これができると、モデルサイズを
   下げても JSON が壊れなくなる。
4. **ライセンスが商用・改変可。** Apache-2.0 か MIT が望ましい。Llama / Gemma 系は
   独自ライセンスなので、使う前に条項を読むこと。
5. **量子化してロボットに載る形式があること**（オンボード実行する場合のみ。3 節）。

## 3. サイズと待ち時間 — Go2 オンボードで動かす（決定済み）

**実行場所は Go2 オンボード（Jetson）に決めた。** これがサイズの上限を決める。

| | |
|---|---|
| 現実的なサイズ | **0.5〜1.7B、4bit 量子化** |
| 150 トークンの生成時間 | 約 3〜7 秒（Orin クラス、llama.cpp Q4、20〜40 tok/s の想定） |
| 参考: 手元の PC (RTX PRO 6000) | 4〜14B で 1 秒未満。**学習と評価専用** |

**出力順は `reply` を先に置く（現状のまま）。** 会話としての体感を優先した結果、
ロボットが動き出すのは JSON を最後まで生成し終えてから、つまり上の 3〜7 秒がそのまま
動き出しまでの待ち時間になる。実機で長すぎると感じたら、手は 3 つ:

1. サイズを下げる（1.5B → 0.5B）。文法制約デコードがあるので JSON は壊れない
2. 返事を短くする（`phrasebank.py` の `REPLY_TAIL` と所要時間の一文を削る。p95 147 → 110 程度）
3. 出力順を `program` 先に変える（`build_dataset.py` の 1 箇所を直して再生成、30〜50 トークン短縮）

1 と 2 は選定後でも効く。3 は方針変更なので、まず 1・2 で足りるか見る。

**推論系。** このリポジトリは aarch64 の ONNX Runtime を落として Jetson でポリシーを回す構成
（`scripts/setup_onnxruntime_jetson.sh`、`deploy/robots/go2/`）だが、ONNX Runtime は LLM 向き
ではない。**llama.cpp (GGUF) を別に持ち込む**のが現実的で、GBNF による文法制約も同時に手に入る。
TensorRT-LLM は速いがビルドと更新の手間が重い。

**システムプロンプト（690 トークン）は削らない。** 内容が固定なので llama.cpp の prompt cache が
効き、2 回目以降のプリフィルはほぼ無料。学習時と推論時で同じものを使うことを優先する。

**先に確認すること:** 実機の Jetson モジュールと空きメモリ。Orin Nano 8GB か Orin NX 16GB かで
1.7B が乗るかどうかが変わる（ポリシー推論と ROS が同居していることも考慮）。ロボット上で
`cat /etc/nv_tegra_release` と `free -h` を見る。

## 4. 学習の要件

- データ 4532 件（train）。**小さい。** LoRA（r=16〜32、2〜3 エポック）を既定にする。
  full fine-tune は 1.5B なら手元の GPU で回るが、雑談能力を忘れる方向に倒れやすい。
- 96GB VRAM なので、学習側はサイズの制約にならない。14B の LoRA でも入る。
  **選定を決めるのは学習環境ではなく 3 節の実行環境。**
- 学習フォーマットは `data/llm/system_prompt.txt` をシステムメッセージに、`input` を user、
  `output` の JSON 文字列を assistant に置く。loss は assistant 部分のみ。

## 5. 評価の要件（選定にも使う）

eval 分割 468 件に対して、候補を 2〜3 個とも同じ手順で測る。

| 指標 | 内容 | 目標 |
|---|---|---|
| JSON parse 率 | 出力がそのまま JSON として読めるか | 100%（制約デコードなら自明） |
| grammar 妥当率 | `program_from_json()` が通るか | 100% |
| program 完全一致率 | 正解プログラムと一致（`roundtrip_check.py` の許容ルール） | 95% 以上 |
| 断り・警告の正しさ | ジャンプを出していないか、倒立・前方回転に警告があるか | 100% / 95% 以上 |
| 未知の言い回し | 学習データに無い言い方を手で 20 件書いて通るか | 目で見る |
| sim end-to-end | 出力プログラムを `validate_programs.py` に流して立って終わるか | 元データと同等 |

比較対象は **ファインチューニング前の同じモデル**（システムプロンプトのみ、few-shot）。
これを超えなければサイズを上げるか、データを見直す。

## 6. 候補

| モデル | サイズ | ライセンス | 備考 |
|---|---|---|---|
| Qwen2.5-1.5B-Instruct | 1.5B | Apache-2.0 | 日本語と JSON が安定。GGUF が揃っている。**第一候補** |
| Qwen3-1.7B | 1.7B | Apache-2.0 | 上の後継。thinking は**切って**使う（この用途に不要で遅くなるだけ）。**対抗** |
| Qwen2.5-0.5B-Instruct | 0.5B | Apache-2.0 | 待ち時間が足りないときの逃げ道。雑談の質は落ちる |
| Llama-3.2-1B / 3B-Instruct | 1〜3B | Llama 3.2 | 日本語は上記より弱い。ライセンス要確認 |
| Gemma-3-1B-it | 1B | Gemma 利用規約 | 多言語は強い。ライセンスが OSI 準拠でない |
| Sarashina2.2 / LLM-jp-3 など日本語特化 | 1〜3B | 要確認 | 関西弁を含む自然さでは有利な可能性。GGUF の有無を先に見る |

オンボード確定なので **3B 以上は候補から外した**。ライセンスとサイズ展開は変わるので、
使う直前に配布元で確認すること。

## 7. 決めたこと / 次の手順

決定（2026-09-11）:

1. 実行場所は **Go2 オンボード（Jetson）**。サイズは 0.5〜1.7B、4bit 量子化。
2. 出力順は **`reply` 先のまま**。データの再生成は不要。
3. 推論系は llama.cpp (GGUF) + GBNF 文法制約を既定とする。

次の手順:

1. 実機の Jetson モジュールと空きメモリを確認する（3 節末尾）。
2. **Qwen2.5-1.5B-Instruct** と **Qwen3-1.7B** の 2 本を同条件で LoRA し、5 節の表で比べる。
   1 本 30 分程度。ここで勝った方を GGUF に変換して実機に載せる。
3. 実機で待ち時間を測り、長ければ 3 節の 1・2 の手を打つ。
